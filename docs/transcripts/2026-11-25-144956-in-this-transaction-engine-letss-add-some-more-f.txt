● Fuzzing is worth adding here, and the library/binary split makes it cheap.
  Your two main ideas need adjusting, though. I'd build two fuzz targets, not
  one.

  1. Fuzzing Engine::apply with raw Records will report a crash that can't 
  happen in production.
  Amount::from_units is public, so a fuzzer that builds Records directly will
  produce deposits of 0 or -5. Those hit the debug_assert!(amount > 
  Amount::ZERO) in Engine::apply (src/engine.rs:214). cargo-fuzz turns debug
  assertions on by default, so this shows up as a panic within seconds. In
  production it can't happen, because csv_adapter rejects non-positive amounts
  as Malformed before the engine sees them. So the engine relies on its caller
  for that guarantee.

  You can either:
  - have the fuzz target generate only positive amounts (simple, and matches the
    current design), or
  - make the type enforce it: a Transaction constructor that rejects amounts ≤
    0, so no caller can build a bad Record.

  I'd do the first now and note the second as a design option. A deposit-only
  amount type would be the cleaner long-term fix.

  2. The CSV fixtures won't help an engine-level target.
  A target that takes Records reads its input as structured bytes (via
  arbitrary), not CSV text. Seeding it with your fixtures gives the fuzzer
  noise, not useful starting points. The fixtures fit a second target that feeds
  bytes through pipeline::run(&data[..], io::sink()). It still skips file I/O,
  because run accepts any Read/Write. That is also where most of the crash risk
  is: untrusted text going through the csv crate, header matching, amount
  parsing and the warning path. The amount parser deserves its own small target
  too, since "1.", ".5", very long digit strings and overflow are classic panic
  sources.

  3. Check invariants, not just "it didn't crash".
  A run that only checks for panics proves little here. Production code has a
  single expect, and the set_balances check already guards it. The engine target
  becomes useful if, after each apply, it asserts:
  - total == available + held and held >= 0;
  - a Rejected record leaves every account unchanged;
  - a locked account never unlocks;
  - a dispute action never creates an account.

  With these checks, a run with no failures shows the README's rules hold for
  any input sequence, beyond the cases the fixtures pick out.

  Proposed layout:
  - fuzz/fuzz_targets/engine.rs: a structured list of operations with small id
    ranges (e.g. client % 4, tx % 16). Without small ranges, the fuzzer almost
    never makes a dispute that hits a real deposit. Amounts are limited to
    positive values, and the invariants above are checked after every step.
  - fuzz/fuzz_targets/csv_pipeline.rs: raw bytes into run. Its corpus is seeded
    from tests/fixtures/*.input.csv, and its dictionary holds deposit, dispute,
    resolve, chargeback, type,client,tx,amount, . and ,.
  - fuzz/fuzz_targets/amount_parse.rs: str::parse::<Amount> round-tripped
    through Display.

  You already have nightly and cargo-fuzz 0.13.2 installed, so nothing else
  needs setting up. arbitrary would be a dependency of the fuzz crate only; the
  main crate doesn't change. The fuzz/ crate stays out of cargo test and stable
  builds. I'd also add a short README section on how to run it.

  Want me to build it that way, with the positive-amount restriction for now?
